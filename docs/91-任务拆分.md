# 这很三国｜任务拆分

《迭代计划》中的每个迭代，在开发前拆分为可独立开发、可独立验证的任务。

## 一、拆分约定

* 编号连续，跨迭代不重排，一个任务对应一次可验证的交付
* 每个任务在自己的层内自洽，验证通过后再进入下一个
* 任务按依赖推进，依赖未完成时不开始被依赖的任务
* 所在层：`docs` 文档 ｜ `core` 规则层（不依赖 Phaser）｜ `app` 装配层 ｜ `ui` 界面外壳 ｜ `game` 表现层 ｜ `test` 测试
* 每个任务记录交付内容、验证方式与当前状态

## 二、迭代 1｜骨架、回合与最小存档

依赖：T1 → T3 → T4 → T5 → T6 → T7；T2 可后置；T8 随 T5、T6 补齐。

**T1 工程脚手架与测试基础设施**（`app`）

* 初始化 TypeScript、Vite、Phaser、Vitest 的工程配置，接入 Phaser 占位场景与 DOM 界面挂载点
* 建立 `core`、`app`、`ui`、`game` 分层，规则层不依赖 Phaser
* 验证：`dev`、`build`、`test` 三条命令均可运行
* 状态：已完成

**T2 GitHub Pages 自动部署**（`app`）

* 配置构建子路径，添加构建后发布到 GitHub Pages 的工作流，部署前先执行测试
* 验证：推送后工作流跑绿，Pages 地址可访问
* 状态：已完成

**T3 领域模型与初始世界**（`core`）

* 定义 `GameState`、`Faction`、`Scenario`，给出建安十三年（208 年）秋开局剧本（曹操、刘备、孙权三家，玩家为刘备，刘备退据江夏）
* 数据按剧本组织，不同时间点的开局各是一份剧本
* 验证：初始状态的日期、回合数、势力列表与玩家势力正确；势力 id 唯一；状态不与剧本数据共享可变对象
* 状态：已完成

**T4 可复现随机数**（`core`）

* 以 mulberry32 实现随机数模块，内部状态为单个 32 位整数，随存档一起落盘
* 全项目仅此处使用 `Math.random()` 生成种子
* 验证：同种子结果一致，不同种子结果不同，状态为无符号 32 位整数
* 状态：已完成

**T5 回合推进与势力行动顺序**（`core`）

* 结束回合推进一季并递增回合数，跨年自动进位
* 行动顺序为玩家势力先行动，其余按势力列表顺序
* 验证：跨年进位正确，行动顺序稳定，玩家势力始终居首
* 状态：已完成

**T6 键位化存档层**（`core`）

* 自动存档与手动槽位共用同一套 `SaveStore` 接口，仅 key 不同；槽位编号从 1 起，共 10 个
* 读取时统一处理无存档、格式损坏与版本不匹配
* 验证：存读往返一致，异常输入返回 `null`，槽位摘要与存档内容相符
* 状态：已完成

**T7 界面外壳与装配**（`ui`、`app`）

* HTML / CSS 界面外壳承载日期、回合、势力列表与操作入口，弹窗承载自动存档与手动槽位
* `GameSession` 持有唯一的 `GameState`，串联开局、读档、回合推进、自动存档与槽位，以订阅方式通知界面刷新
* 界面不维护第二份数据
* 验证：结束回合界面同步刷新；保存与读取生效；整页刷新后进度保留
* 状态：已完成

**T8 规则层无画面验证**（`test`）

* 以整合用例验证规则层可在不启动画面的情况下推进与存取
* 验证：推进 120 个季度（30 年）得到正确的年份、季节与回合数；同种子重复推进状态完全一致；开局到存读档的完整流程不依赖画面
* 状态：已完成

## 三、迭代 2｜最小战略地图

依赖：T12 之后 T13、T14、T15 可并行；T16 与 T17 收尾。

**T9 地理表述统一**（`docs`）

* 地理基本单位统一表述为「战略点」，写明战略点不以行政级别为限、区分城市 / 关隘 / 野地类型、州仅作地理分组
* 给出战略点的选取原则：州治 + 关隘 + 名城战场
* 验证：文档中地理基本单位的表述一致
* 状态：已完成

**T10 地理模型**（`core`）

* 定义 `Province`、`Site`、`Geography` 并并入 `GameState`
* 战略点记录类型、所属州、归属势力（可为空）与相邻关系
* 提供校验规则，检查标识唯一、引用完整、邻接对称且无自相邻
* 验证：自洽数据无问题，各类数据错误各自被指出
* 状态：已完成

**T11 战略点数据集**（`core`）

* 地图覆盖十三州，州界取自彩色分区底图，其中九个州共四十九个战略点，含州治、关隘、名城与战场，按剧本挂载
* 曹操 23 点、孙权 7 点、刘备仅江夏，其余 18 点无归属
* 相邻关系由地理推导而非手工编排：两点之间若存在第三个战略点则不相邻，邻接表按距离升序排列
* 验证：数据自洽；从江夏出发可达全部战略点
* 状态：已完成

**T12 地图布局与渲染骨架**（`game`）

* 按真实经纬度投影确定战略点坐标，按类型画成不同形制（城市为圆、关隘为菱形、野地为淡底方框），颜色按归属着色，无归属用中性色
* 建立战略点 id 到屏幕区域的查询接口，供点击与悬停使用
* 验证：打开页面即见着色正确的天下图
* 状态：已完成

**T13 州的分组展示**（`game`）

* 绘制十三州的州界轮廓并标注州名，轮廓由底图彩色分区栅格化后抽稀得到，相邻州共用同一批顶点，接缝既不重叠也不留空隙
* 验证：十三个州的划分可辨认
* 状态：已完成

**T14 相邻关系表达**（`game`）

* 绘制相邻战略点之间的连边，悬停时高亮该战略点及其邻域
* 验证：任意战略点的邻域一目了然
* 状态：已完成

**T15 玩家领土高亮与图例**（`game`）

* 强调描边玩家所辖战略点，图例列出颜色与势力名
* 验证：玩家领土一眼可辨，图例与侧栏势力一致
* 状态：已完成

**T16 解耦回归**（`test`）

* 确认结束回合不改变地理结构，地图只读 `GameState`，`core` 不依赖 Phaser
* 验证：规则验证与代码检查
* 状态：已完成

**T17 地图拖动与缩放：镜头可平移缩放，开局聚焦中原与荆襄**（`game`）

* 沿用底图分区的州界；取消边缘截断，画布铺满可用区域，镜头支持拖动与滚轮缩放
* 验证：操作验证：画布填满区域且无留边，拖动可看到全部十三州，滚轮在限制范围内缩放，开局视图位于中原与荆襄
* 状态：已完成

## 五、迭代 3｜行动力与人才寻访

依赖：T18 → T19 → T21；T20 → T21；T22 依赖 T21；T23 收尾；T24 随 T20、T21 补齐。

**T18 行动力模型**（`core`）

* `GameState` 增加当季剩余行动力；每季预算与各项行动的消耗集中定义为常量表，初值取每季 4 点、寻访 1 点，供迭代 5 按实测调整
* 结束回合时把剩余行动力重置为当季预算
* 存档版本递增，使旧存档失效
* 验证：新开局与结束回合后行动力等于当季预算；扣减不会使剩余为负
* 状态：已完成

**T19 行动流程与行动记录**（`core`）

* 统一行动流程：校验前置条件 → 校验行动力 → 扣除 → 执行规则 → 更新状态 → 产生记录
* `GameState` 增加本季行动记录，记录行动类型、目标与结果；结束回合时清空
* 验证：前置条件或行动力不满足时整体拒绝且状态不变；成功时按流程扣减并追加记录；结束回合后本季记录清空
* 状态：已完成

**T20 武将模型与人物数据**（`core`）

* 定义最小武将：标识、姓名、状态（在野 / 在仕 / 退场）、所属势力（可为空）；战斗属性留待迭代 4
* 定义麾下武将上限常量（初值 30，可调）与不变量：在仕武将数不超过上限，在野与退场不计入；本迭代上限只作安全阀，解任与替换留待迭代 9
* 入仕与否由状态决定，在野者可入仕，不由随机决定，使「发现谁」成为寻访唯一的随机环节
* 给出建安十三年的人物数据，按所在州分布，供寻访抽取
* 并入 `GameState` 与剧本，校验引用完整
* 验证：标识唯一；所属势力引用有效；状态与所属势力自洽；入仕判定不依赖随机
* 状态：已完成

**T21 人才寻访与双随机源**（`core`）

* 引入两条互不干扰的随机流：模拟流沿用现有 `randomState`，随存档落盘、可复现；抽卡流会话级、不落盘、随会话播种，读档与刷新都不回退
* 寻访只消耗抽卡流：范围以玩家势力当前占有战略点所在的州为准，本迭代该州为单一卡池，按州控制分级的卡池留待迭代 4
* 在该州在野武将中抽取候选，在野者立即入仕玩家势力，忠诚等留待迭代 7
* 前置条件含「在仕武将数未达上限」（见 T20），满员或该州无可寻之人时拒绝、不扣行动力
* 寻访以传入的随机源为参数，规则层保持不依赖会话的纯函数
* 验证：范围外的武将被排除；满员或无可寻之人时明确失败且不扣行动力；同一抽卡源下结果可复现；读档后重复寻访会消耗抽卡流的下一个值，不复现上一候选
* 状态：已完成

**T22 界面：行动力、寻访与行动记录**（`ui`、`app`）

* `GameSession` 暴露寻访接口；侧栏显示本季剩余行动力、寻访按钮与本季已执行行动
* 行动力不足或无可寻访对象时给出明确反馈
* 验证：操作验证：寻访后行动力、行动记录与势力武将同步刷新；行动力用尽后无法再寻访
* 状态：已完成

**T23 行动力与寻访无画面验证**（`test`）

* 不启动画面走完：寻访 → 扣减 → 记录 → 结束回合恢复
* 覆盖双随机源：模拟流固定种子可复现；寻访注入固定抽卡源时可复现，且读档不回退抽卡流
* 验证：固定种子下模拟结果一致；行动力不足被拒；结束回合后预算恢复；读档后重复寻访不复现上一候选
* 状态：已完成

**T24 文档同步**（`docs`）

* 《产品设计》补记行动力数值口径与寻访规则；《想法记录》将相关约定记入已完成
* 核对《游戏机制》《技术设计》中行动力、寻访、双随机源的表述与实现一致
* 验证：三处文档与实现表述一致
* 状态：已完成
