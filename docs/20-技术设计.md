# 这很三国｜技术设计

## 一、技术目标

游戏首先作为一个纯前端 Web 游戏运行。

初版不依赖后端、不要求账号、不需要购买服务器或域名。

目标是：

```text
浏览器
 ↓
加载静态资源
 ↓
在本地运行完整游戏
 ↓
本地保存游戏状态
```

部署采用 GitHub Pages。

## 二、技术栈

初版采用：

```text
TypeScript
Phaser 4
Vite
GitHub Pages
```

其中：

* TypeScript：游戏规则、状态与业务逻辑
* Phaser：2D 渲染、输入、场景、动画及游戏运行时
* Vite：开发、构建与静态资源打包
* GitHub Pages：静态网站部署

不引入 Java 后端。

不引入 React 作为游戏主框架。

## 三、整体架构

游戏逻辑与表现层分离。

```text
                Phaser
                  │
           游戏表现与输入
                  │
                  ↓
             Game Core
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
      Model     Rules    Simulation
        │         │         │
        └─────────┼─────────┘
                  ↓
              GameState
                  │
                  ↓
              SaveStore
```

核心原则：

> **游戏规则不依赖 Phaser。**

地图怎么画、按钮怎么显示、动画怎么播放，不应决定“这一季发生了什么”。

游戏规则应该可以在没有真实游戏画面的情况下独立运行。

## 四、核心状态模型

整个游戏围绕一个统一的 `GameState` 运行。

概念上包括：

```text
GameState
├── currentDate
├── currentTurn
├── actionPoints
├── actedCharacterIds
├── contactedCandidates
├── captives
├── history
├── firedEvents
├── relations
├── playerFaction
├── outcome
├── endedTurn
├── geography
├── factions
├── characters
└── randomState
```

`geography` 描述州与战略点的地理结构。战略点是领土与进攻的基本单位，分都会、大城、小城、关隘、野地五类，类型决定人口上限、开发等级上限与据点防守补正（野地人口为 0、不可建设、不产兵粮，也没有防守补正，却并入行军图，与城池、关隘同为据点：可驻一名武将、可被攻占，也计入势力存亡）；记录其类型、所属州、相邻关系、当前归属势力（正式剧本全图尽归势力，数据上允许为空）、人口 `population`、存粮 `granary` 与三项开发等级 `development`（农田、市集、民居）。人口是存粮与兵源的共同基础，随地块走，不因易主而清空；存粮落在点上，每季随人口增加、有上限，易主后归新主。存粮与开发等级皆为剧本可省略项，开局由 `cloneGeography` 补上（存粮取一季的增量），由 `granary.ts` 与 `development.ts` 结算与提升，仍随存档落盘。守备全由势力的武将构成：每处战略点至多一名驻将，由武将的 `stationedSiteId` 指向该点，没有独立于武将体系的常备武装。战略点在地图上的坐标与形状属于表现层，不进入状态。州是地理分组，用于地图展示与寻访范围；州归属按城池与关隘的占点多寡判定，野地不计入，与他方并列时原归属者保持，因而须存状态，不能只由当前版图推出。

### 地图数据基准

州轮廓取自彩色分区底图，边界形状与底图一致，以建安十三年（208 年）的州制为准：

* 司隶领河东、河内、河南尹、弘农与三辅，建安年间司隶校尉督关中，长安属司隶。
* 凉州领陇右诸郡与河西四郡，武都、阴平自益州还入；汉中的底图分区与陇右同色，一并归凉州。
* 河西与陇右在底图上同用一片绿色，同属凉州；西海在底图上留白，不划入；居延的底图分区与河西同色，归凉州。
* 并州北缘含朔方、五原、云中，上郡故地（延安—榆林带）随底图分区并入并州。
* 底图未着色的地带（如阿拉善、鄂尔多斯、青海一带）不属任何州，保持无主；交州的下边界照底图的交州分区重描，西界沿底图分区的无主地一侧，海疆亦依底图轮廓；交州以南底图覆盖范围内的塞外陆地以底图为准，珠江口西岸的南沙、中山、珠海一带在底图上不着色，作无主陆地。
* 海岸线取历史岸线：渤海湾的现代黄河三角洲、苏北海岸与长江口北、珠江三角洲在近千年才淤积成陆，建安年间尚为海面或滩涂，不划入任何州，保持无主。
* 近岸岛屿的处理与参照底图一致：崇明、舟山群岛等保持无主，不并入最近的州。
* 塞外陆地不越出制图范围：南界止于北纬 16.3°，其以南的陆地与岛屿一概不取。

`factions` 记录势力：标识、名称、颜色、粮食 `grain` 与金钱 `money`。粮食用于征兵与维持部队（初版的两项资源之一），金钱是经营、外交与人事的专用资源——军队维持不吃钱。粮食落在两块地方：各战略点的存粮 `Site.granary`（`granary.ts` 定义增量、上限与运回比例）与势力粮仓 `grain`。每季由 `settleGrain` 结算：先令各点存粮增加、止于上限，再把各点存粮按比例运回入库（`shipGranary`），扣除在仕部队按规模计的军粮（兵力 × 0.01）。界面上的运回与净收支（`granaryIncome` / `grainBalance`）按同一口径估算——先加本季增量再取六成，故预览值即是结算后到账的那一笔。结余入库；收不抵支时粮仓归零，**不做减员**——欠粮只体现为征兵与出征做不了。另有主动征粮（`harvestGrain`，在本方任一战略点发起，从名册中选一名武将执行，自该点存粮中取用，产量由内政与兵力共同决定，取量不超过该点存粮）。金钱每季由 `settleMoney` 按各战略点人口的税收入库（人口 × 0.002），支出（建设、外交与赏赐）只在行动发生时扣除。具体数值见《游戏机制》。

`characters` 记录武将：标识、姓名、状态、所属势力与所在州，以及武力 `might`、统率 `command`、智谋 `intellect`、内政 `politics`、性格 `personality`（取自集中定义的少量标签，决定基准招聘成功率）、势力倾向表 `affinities`、忠诚 `loyalty`、君主标记 `isMonarch`、兵种 `armType`（步兵 `infantry` / 弓箭手 `archer` / 骑兵 `cavalry`，随人而定且为必填）、驻守战略点 `stationedSiteId`（驻守的自有战略点，未驻守为 null）、兵力 `troops`、带兵上限 `troopLimit`、出战经验 `exp`、已用强化次数 `boosts` 与寻访卡池层级 `tier`。在野者只记所在州，在仕者列入所属势力的名册，驻守只是名册内的一项指派、可以不驻守；年龄随人物数据给出，随年份增长。带兵上限、出战经验与强化次数为可省略项：带兵上限未记时按统率折算，经验与强化次数未记时视为零。成长见 `growth.ts`。士气不在这里——它是战斗属性，见「战斗系统」。

未出仕的武将是 `characters` 的一部分，不另外维护人才池。

`relations` 承载势力之间的关系：一张对称的势力对表，每条含状态（同盟 / 敌对 / 中立）与好感 `favor`（0–100，50 为中性）；未声明的势力对为中立、好感取中性。状态决定能否开战与用兵，好感决定外交的门槛与成败；查询与调整集中在 `src/core/relations.ts`（`relationBetween`、`favorBetween`、`setRelation`、`adjustFavor`）。外交动作在 `src/core/diplomacy.ts`：宣战与停战改状态，赠礼与索取动好感，结盟与停战另以好感门槛加上对方的一次应答判定。他方的外交决策在 `factionAi`——对高好感的中立方提议结盟；他方守成，不自行宣战，点火改由玩家的宣战。武将之间的关系属于另一个独立系统，初版不实现。

`history` 保存行动历史（类型、势力、时间、目标、结果），供表现层展示，不参与规则计算；回合推进不清空，全局累积。

开局由剧本（`Scenario`）给出：初始日期、玩家势力、势力与其粮钱、势力间的初始关系、地理与人物。`SCENARIOS` 汇集可选剧本，界面「新游戏」按所选剧本重建 `GameState` 并覆盖自动存档。剧本是纯数据，规则层与界面都不为某个剧本写分支。

正式剧本只有「建安十三年」一家，取重绘的版图与合并后的人物表。另有「荆扬一隅」：只取十点、三家的缩样，地理自成一夹具（`geographyAcceptance.ts`），人物仍取自正式人物表、只在开局的驻守与兵力上覆写，供无画面推演与连续游玩的快速验收，不改动正式剧本的任何数据。

具体模型根据实现逐步细化。

原则是：

> **世界状态只有一个事实来源。**

界面不自行维护第二份武将、战略点或资源数据。

## 五、规则系统

规则系统负责根据当前状态计算结果。

例如：

```text
advanceTurn()
resolveFactionActions()
resolveResourceProduction()
resolveConstruction()
resolveTalentSearch()
resolveConscription()
resolvePersonnel()
resolveDiplomacy()
resolveBattles()
resolveProvinceOwners()  // 占领后重算州归属
resolveFactionStatus()
resolveEvents()
updateOfficerStates()
```

这些操作应尽量保持确定性、可测试，并通过明确的输入与输出修改 `GameState`。

当前已实现的规则：回合推进（`advanceTurn`，含粮食结算 `settleGrain`、金钱税收结算 `settleMoney`、各战略点人口缓增 `growPopulation` 与带兵上限随季增长 `growTroopLimits`）、寻访人才（`seekTalent`）、征兵（`recruit`，先选站点再从名册选人）、征粮（`harvestGrain`，先选站点再从名册选人）、内政建设（`build`，见 `src/core/development.ts`）、驻守任命（`assignStation`）、进攻与战斗（`openAttack` / `currentActor` / `resolveAction` / `finishBattle`，六阵位布阵、逐次行动与战后结算）、外交（`src/core/diplomacy.ts`：宣战、停战、结盟、赠礼、索取；关系查询见 `src/core/relations.ts`，名下已无战略点的势力不再计入敌对）、人事（`src/core/personnel.ts`：解任、赏赐、遣散）、武将成长（`src/core/growth.ts`：出战计数与强化）、胜负判定（`src/core/victory.ts`：己方覆灭即失败、其余势力全部覆灭即统一，覆灭与结算见《游戏机制》）；其余为后续迭代的规划。

### 随机性

游戏包含人才寻访、事件、战斗等随机结果。

随机数集中管理，并支持可复现的随机种子；分两条互不干扰的流：模拟流内部状态随存档落盘，用于战斗、AI 与事件等世界演化，同一存档可复现同一结果；需要玩家逐步介入的战斗把随机流随战斗状态一同携带，结束时写回全局状态；抽卡流按回合播种、不落盘，用于玩家主动发起的抽取——同一回合里无论刷新还是读档，抽取结果一致，不能借 S/L 重掷。

集中管理便于重现问题、调试异常战斗与验证规则，也为未来的固定种子或挑战模式留出基础。

## 六、行动力系统

行动力属于游戏规则层。每项行动声明自己的行动力成本，成本集中在常量表中定义，不散落在规则里；具体数值见《游戏机制》。

行动力按势力分别存放：`GameState.actionPoints` 是「势力 → 剩余行动力」的映射，各势力每季各有一份预算，互不占用。行动的统一入口 `runAction` 据此从发起行动的势力名下扣除，取值缺省为玩家势力——玩家各动作的调用方式不变，其他势力则显式传入自己的标识。

行动执行流程：

```text
玩家请求行动
 ↓
检查前置条件
 ↓
检查行动力
 ↓
扣除行动力
 ↓
执行规则
 ↓
更新 GameState
 ↓
写入行动记录
 ↓
刷新界面
```

## 七、武将与势力系统

势力通常由君主统领，君主是该势力中的一名武将，每个势力至多一名君主；势力自身记录标识、名称、颜色、粮食与金钱，粮仓之外另有落在战略点上的存粮。袁氏是唯一的无君主势力——袁绍已死、三子相争，只列部属，不设君主。

解任与赏赐在 `src/core/personnel.ts`：`dismiss` 把在仕武将罢为在野（复用俘虏释放的 `becomeWild`），`reward` 花金钱提升忠诚，`disband` 把兵力减到指定数量且不耗行动力。君主不可解任。

武将的字段见「核心状态模型」中的 `characters`。四项能力分工明确：统率决定兵力（征兵产量与带兵上限，征兵另受所选战略点的丁口所限），武力参与伤害、统率参与减伤，内政与兵力共同决定征粮产量；智谋暂不介入普攻，留给日后的法伤与魔抗。

兵力直接记在武将身上（`troops`），势力不存在脱离武将的兵力；每名武将一个兵种（`armType`），随人而定、不随战事改变，征兵只补充该兵种的数量。

**兵只从征兵来**：武将自己不长兵，每季只增长带兵上限（`growTroopLimits`），实际兵力一兵不增。新入仕者（寻访与劝降归附）兵力为零。征兵（`recruit`）是唯一的补兵手段，产量按统兵者的统率换算、粮食按同一基准消耗，并占用该武将本季的行动。征兵另受所选战略点的丁口所限：丁口为该战略点人口的百分之二（`sitePopulationCap`），一次至多抽走这么多，所征之兵自该点人口中扣除，丁口不足则不能征。带兵上限为武将身上的状态（`troopLimit`），开局与入仕时取统率 × 150，每季再按统率 × 2 增长、封顶 99999；征兵补到上限即止。出征另需用粮，按投入兵力换算（`attackGrainCost`），粮草不足则不能出阵。粮食的收支与缺粮后果见「核心状态模型」中的 `factions`。

武将成长在 `src/core/growth.ts`：每名武将有一次出战经验（`exp`，进攻与防守中各按胜负记一次——胜 +2、败 +3，败仗反而长进更多），每累计 `EXP_PER_BOOST` 点得一次强化额度；攒够额度即可用 `strengthen` 选一项能力提高 `BOOST_GAIN` 点，消耗行动力、与本人本季是否已行动无关，每人累计至多 `BOOST_MAX` 次、单项能力封顶 120。人物数据按本色取值、载入时只把越界的数值截断，成长另设高于本色的上限。

士气是战斗状态，不落在武将上：每场战斗各有一方共用的士气，开战 100、下限 40，每有一队退场该方士气 −5，只用于该战的伤害与减伤计算。

`status` 描述武将的处境：在野、在仕、被俘、退场。战略点失守时，参战与驻守的武将按权重判定撤回、战死或被俘；被俘者押入俘获方的俘虏营（见「俘虏营」），无城可投的逃亡者流落为在野。退场者（战死或被斩杀）不再参与游戏：名单、候选与一切结算统一按「在仕」（`isServing`）与「退场」（`isRetired`）两个判定取用，不散落 `status` 字面，年龄也不再为其增长，开发者模式的全量列表是唯一例外。

`affinities` 是对各势力的偏好表（0–100，50 为中性），未记录的对按 50；`loyalty` 是忠诚，与偏好无关——偏好是感觉，忠诚是价值观，随经历变化。界面不露出偏好数值，改由 `affinityAttitude`（见 `src/core/affinity.ts`）分档为「亲附 / 中立 / 疏离」，武将卡的年龄亦然另作呈现（不足二十岁记「未冠」）。

寻访在发现候选后按「性格基准 × 偏好系数」判定招聘（见 `src/core/seekTalent.ts`）：成则经 `join` 入仕，并按其对己方的偏好定忠诚初值（`joinLoyaltyFor`，与俘虏归附共用）；败则人留在野，并记入该势力的接触名单 `contactedCandidates`（连同会面之处），行动力照扣。可再花行动力「拜访」——每次使该武将对己方的偏好随机上升 5–15，再判定一次。未招到前他仍在野，他方寻访也可能把他招走。招降如何取用忠诚见「俘虏营」，忠诚的变化与叛离见下段；挽回忠诚的手段见上文的赏赐。

`loyalty` 只降不升，且只落在当事人：驻守的战略点失守、驻将撤出 −10（`finishBattle`），参与进攻失败者 −8（`finishBattle`），君主不计。挫折发生时调用 `maybeDefect`（见 `src/core/loyalty.ts`）：忠诚低于其叛离阈值的在仕者离走，转为在野——州取本人所在州（`provinceId`）、卡池层级按能力给（四项最高 ≥ 85 进二级池，其余基础池）、对原势力偏好 −30、清出接触名单，并写一条 `defect` 记录（历史照旧按势力分组）。阈值以 40 为基准、随对主家的偏好小幅浮动（`defectThresholdFor`：偏好每偏离中性 1 分反向移动 0.12，两端 ±6），故疏离者更早离心、亲附者多容得下一点挫折——偏好只作微调，决定去留的仍是忠诚。忠诚低而未再受挫者不离开，等下一次触发；离间、笼络尚未做。回归在野者的卡池层级与战败流落共用 `wildTierFor`。界面的「离心 / 不满」提示（`loyaltyHint`）按同一阈值随人浮动，免得提示与实际去留不符。

## 八、战斗系统

战斗系统接收双方部队及环境状态，生成战斗结果。

输入包括：

```text
参战武将
布阵（前排 / 后排）
兵种
兵力
据点类型
士气
逐回合指令
```

输出包括：

```text
胜负
伤亡与剩余兵力
士气变化
武将去向
占领结果
战斗日志
```

战斗结算与展示分离：规则层只产出胜负、伤亡与占领结果并写入历史与战报，表现层读取这份结果，将来加入战斗动画也不必重写规则。战略点易主时，规则层另按本场战斗的随机流令前任已开发的设施随机降 1–2 项（`damageOnCapture`，每项降一级、最低归零），并把它并入行动记录的结果描述。占领不会把参战者留在新点，驻将事后经战略点窗口另行任命（`assignStation`）。

初版不实现单位实时寻路与即时操作。

初版在规则层直接推演，不单独实现战斗场景。一场进行中的战斗由 `BattleState` 承载：双方的参战队与六个阵位、每队的战兵、行动条进度与防御状态、每方共用的士气、当前出手者与累计行动次数、是否已分胜负，以及这场战斗自带的随机流。

进攻的入口是 `openAttack`：校验目标与出征者（`attackBlockReason`，不扣行动力）、扣除行动力与按投入兵力换算的粮草（`attackGrainCost`），排定攻方阵形后开战。`isAttackable` 判断目标是否归属他方、已宣战且与自有战略点相邻——全图没有无主战略点，同盟与中立都打不得；`attackCandidates` 列出名册中未驻守、有兵、本季未行动的武将（已行动的也在列，由界面标为不可选）。守方势力即目标的归属势力（`defenderFactionAt`），守将由 `defenderCandidates` 给出：该点驻将（有兵时自动上阵）与名册中未驻守、有兵、本季未行动的武将。守方无人可守时不战而下，攻方照付行动力与粮草。

布阵名额：双方各六个阵位，前三后三，前排至少一队；攻方从名册中选一至五名武将，守方自选一至五名加驻将、至多六队。`autoFormation` 按兵种排出默认阵形（近战在前、弓手在后，同类按名册次序），`setUnitSlot` 在开打前换位（目标阵位有人则互换），`deployDefenders` 排定守方阵形（给空数组即不战而下）。`targetsFor` 划定一队的可打目标：近战只及敌方前排，前排已空时及于后排；近战若站在自家后排而自家前排尚有人，被本阵挡住、无目标可打，只能防御；弓箭手不受此限。

交锋由 `currentActor` 与 `resolveAction` 驱动：每队沿行动条按「兵种机动 × 速度扰动」累积，满 `ACTION_THRESHOLD` 即行动，行动后扣去满值、余量留待下次；`currentActor` 给出行动条上先满的一队，进度相同时攻方先行、再按阵位，`resolveAction` 结算它的攻击或防御并返回一份行动结果（出手者、目标、伤害、自损、退场者、累计次数）。速度扰动在开战时掷一次、此后每次行动后重掷，幅度 ±10%，随机取自战斗自带的随机流，故同兵种也有先后之差。双方合计行动二十五次为限。他方的指令由 `autoOrderFor` 给出，玩家不参与的交战由 `autoBattle` 按同一套规则推演到底；守方始终无人布阵时按不战而下处理。二十五次内守方全灭则攻方得胜，次数用尽而守方尚有在场者则守方守住。伤害取攻方的兵力、兵种、武力与士气，减伤取被攻击一队的兵力、兵种、统率与士气，守方全员另享据点防守补正（按战略点类型分档，见《游戏机制》）；步兵防御时覆盖自己所在的一排，其余兵种只守自己，防御持续到自己下次行动。智谋不参与普攻，留给日后的法伤与魔抗。战斗随机流在结束时写回 `state.randomState`，固定种子下同一场战斗可复现。

战后由 `finishBattle` 结算：按开战兵力与结束战兵的比例折算实际减员（未折算的部分视为溃散归队）；攻方得胜即占领该点、清出原驻将、按权重判定守方参战者的去向（撤回名册、战死或被俘，驻将撤出者忠诚 −10），随后触发战火损耗、重算州归属并检查守方是否覆灭；攻方失利则参战者回名册、忠诚 −8，不发生俘获。参战的攻方与守方自选武将一律记为已行动，驻将不受此限。被俘者由 `takeCaptive` 押进俘获方的俘虏营，逐人的去向写入行动记录。势力是否覆灭由 `isFactionDestroyed` 判定——失去全部战略点（野地同样计入），或麾下不再有任何在仕武将；界面据此在势力栏标出「已覆灭」。

结算还给出一份战报（`BattleReport`）：攻守双方的参战武将、投入兵力、伤亡与剩余，以及被俘者的态度（`captives`）。战报随行动记录写入历史，界面读取后在战后展示：被俘者另由俘虏窗口单独展示；伤亡与剩余只反映战损，不含失守后撤退、战死或被俘的武将。将来加入战斗动画时复用同一份战报。

俘虏营（`captives.ts`）：被俘者状态记为 `captured`，记入俘获方的 `GameState.captives`（含原属势力与劝降意愿）。意愿只作数值推进，界面按五档（宁死不屈 / 不卑不亢 / 意有所动 / 心动 / 愿降）展示。`persuade` 花行动力依性格与忠诚抬升意愿，升到阈值即经 `joinLoyalty` 入仕；`releaseCaptive` 释放为在野（按能力定卡池），`executeCaptive` 令其退场；君主既不可劝降也不可释放。某势力覆灭时，它营中的俘虏由 `releaseCaptives` 一概开释为在野（按能力定卡池），旧主正是攻方者也不例外。其他势力的俘虏由其每季只把已「愿降」者收为己用（`recruitWillingCaptives`），不主动劝降。归附经 `serveUnder` 落点：该势力麾下已达上限（30）时不再接收，此人转为在野。

驻守是名册内的一项指派：`assignStation` 指定某点的驻将（传 null 撤下现任），每点至多一人，耗 1 点行动力，不改变武将的已行动状态；换人时原驻将自动卸任。驻将不能出征，也不占守方自选的名额，每次该点被攻都自动上阵（兵为零者不上阵），一季之内次数不限，也不因防守转为已行动。野地同为据点，可驻一名武将、可被攻占。

界面的战斗演出分三步：布阵幕（亮出敌方阵形、武将、兵种与兵力，我方六个阵位可拖动或点选互换；守方另选迎战者）→ 逐次交锋（每队卡上有兵力条与行动条；行动条以步兵机动 10 走满 2 秒为基准，其余兵种按机动分得时间，条子匀速增长；开战第一幕从零涨起，涨满之后才亮起行动者与攻击／防御按钮，敌方满条后再留 0.8 秒才出手，不直接跳到结算值；轮到我方某队时，攻击按钮落在可打的敌军身上、防御按钮落在该队自己身上；他方由规则层自动下令，按节拍演出；「自动战斗」可随时切换，自动时我方也交给规则层下令，行动条与行动间隔各减一半）→ 战后结果（战报与伤亡）。攻守两种站位共用一套演出，只是「我方」换了一侧。编成窗口的标题写作「进攻 · 江陵」，窗内左上提示「请选择武将」、右上记「可选 x / 5」，底部另设「放弃战斗」，没有可出战者时也能退出；战斗窗口只留「战斗」或「防守」，右上角记「剩余回合数 x / 25」，战况列在战场右侧，每条交手连同自损一并记下。摆阵幕亮出的敌军阵形即开战前的敌情，界面另以 `attackBlockReason` 在开战前拦下不合规的出征。战斗窗口不设关闭按钮，也不响应 Esc；放弃只在摆阵幕与编成窗口的「放弃战斗」上发生——主动进攻退回行动力与粮草，等同没有开战；守方放弃即不战而下。规则层只按这一套状态机推演：布阵、逐次结算与战后结算皆在其中，界面只读取状态、回传指令。

## 九、世界模拟

其他势力不能直接调用 UI。

其他势力的主要行动对玩家可见。

它们通过统一的势力决策接口执行行动：

```text
FactionDecision
    ↓
Action
    ↓
Rule Validation
    ↓
Execute
```

初版 AI 采用规则驱动，而不是 Agent。

他方对他方只知大概：决定是否出阵、是否应允外交时所据的对方实力，都取估计值（在真值上下摇摆一个幅度，见 `intelligence`），不再有一条固定的胜负线。

决策主要依据：

* 当前资源
* 领土
* 敌我关系
* 军力
* 人才
* 安全程度
* 势力目标
* 当前局势

目标是让各势力具有可理解的行为倾向，而不是追求真正意义上的智能。

初版的最小行为集为寻访、外交、征粮、进攻与征兵，集中在 `factionAi`：`factionTurnStream` 让每个非玩家、未覆灭的势力依次出手，顺序为寻访（补人，新人当季即可参战）→ 外交（对高好感的中立方提议结盟；他方守成，不自行宣战）→ 征粮（粮仓低于保留值才派内政最高者在存粮最多的自有战略点征收）→ 进攻（只在已宣战势力的相邻战略点中挑可胜且价值最高者，出征队伍取名册中未驻守、有兵、本季未行动的武将）→ 征兵（把余下行动力用尽）；营中已到「愿降」的俘虏在出手之初先行归附。所有行为都走规则层已有动作，不新增规则；行动力、粮食、人口与带兵上限的约束与玩家一致。

其他势力不再使用玩家那套按回合播种的抽卡流，寻访与战斗的随机都取自随存档落盘的模拟流，因此固定种子下他方的行为序列可复现。回合收尾为「其他势力行动 → 世界结算 → 进入下一季」；他方的行动与玩家一样写入历史，界面按势力分组展示，无需另做入口。领土归属与兵力随之每个回合都在变。

**回合可暂停**：他方来攻我方时，`factionTurnStream` 以生成器停在那次进攻上，交回一条信号——先给出「待布阵」的请求（`DefenseRequest`：来犯势力、目标与已排好攻方阵形的 `BattleState`），等界面以守方的迎战布阵作答后，再交出这一战的战报，然后继续本回合。`turn.beginTurn` 返回的 `TurnRun` 就是这条推进线；`turn.endTurn` 则一路按自动布阵放行并进入下一季，所以无画面的推演与测试照旧。界面侧的 `GameSession.endTurnStaged` / `deployDefense` / `finishDefense` / `continueTurn` 逐次推进，跑完才写入自动存档；每一步之后都结算一次结局，玩家中途覆灭即停下。

## 十、事件系统

事件采用数据驱动方式：每季结算前求值一次，筛出条件全满足、权重为正且未触发过（一次性）的候选，按权重抽一件施加，写入历史（一条不属任何势力的记录）。新增事件只加数据；条件与效果是固定词表，要加新机制才需改代码。

一条事件：

```text
EventDefinition
├── id
├── text        触发时写入历史的一句话
├── once        触发一次后不再候选；缺省可反复触发，由条件自限
├── weight
├── conditions  全部满足才成为候选
└── effects
```

### 条件与效果

条件与效果都取自固定词表，一一转发给既有模块，不借单个事件引入新机制。

条件：

```text
date          日期落在给定时段内
factionAlive  势力仍在
relation      两势力关系为指定状态
favor         两势力好感落在给定上下限内
resource      势力粮食或金钱低于给定值
```

效果：

```text
setRelation     改两势力关系状态
adjustFavor     增减两势力好感
adjustGrain     增减势力粮食
adjustMoney     增减势力金钱
adjustLoyalty   增减在仕非君主武将的忠诚
adjustAffinity  增减武将对某势力的倾向
```

### 事件约束

事件的 `effects` **只能操作已有的游戏属性与状态**，目标不存在时静默略过，不允许通过事件新增游戏的基础机制。事件一律自动结算，结果只是既有属性与状态的变化。

不允许事件直接引入：

```text
new_relation_type
new_combat_rule
new_action_type
new_resource_type
```

除非该机制已经正式成为核心游戏规则的一部分。

这样可以保证新增事件主要是内容扩展，而不是底层系统扩展。

### 事件执行

事件处理流程：

```text
检查触发条件
 ↓
选定事件
 ↓
施加 Effects（转发给既有模块）
 ↓
修改 GameState
 ↓
写入历史
```

规则与表现分离：事件只在状态上留下与普通行动同样的痕迹，界面按既有方式展示，不参与事件判断。

### 后续扩展

如果后续某类事件被验证为具有足够的游戏价值，可以将其从普通属性事件扩展为持续效果或专属机制。

这种扩展应作为核心规则演进处理，而不通过普通事件系统绕过现有边界。

## 十一、存档

初版采用本地自动存档。

存储：

```text
SaveData
├── schemaVersion
└── gameState
```

`randomState` 属于 `gameState` 的一部分，随其一起落盘。

`schemaVersion` 现为 99：世界结构或既定数据的改动会使之递增，与存档版本不符者随即失效。载入时另做必需字段与类型校验，结构半损的存档一律落回空，不带进对局。写入失败（存储不可用或配额用尽）不抛错，回报失败并由界面提示，上一份存档仍可读回。

进入下一回合时自动保存；行动本身不落盘，读档或刷新会退回到本回合开始时的进度。

保存层定义抽象接口：

```text
SaveStore
├── save()
└── load()
```

初版实现：

```text
LocalSaveStore
```

实际存储优先使用 `localStorage`；只有当后续状态规模明显超出适合范围时，再考虑迁移至 IndexedDB。

保存数据必须带版本号，以支持未来数据结构升级。

## 十三、资源与美术

所有游戏资源作为静态前端资源随版本发布。

建议统一：

```text
assets/
├── portraits/
├── map/
├── icons/
├── ui/
├── effects/
└── audio/
```

图片、图标和音频不参与游戏规则。

武将头像、地图、UI 等美术资源只承担表现职责。

第一阶段允许使用临时素材占位，以保证玩法优先。

正式资源应尽量统一画面比例、构图与视觉语言，形成项目自己的美术体系。

## 十四、未来 Agent 能力

Agent 不属于初版核心架构。

未来如果加入 Agent，应作为可替换的决策实现，而不是让 LLM 直接修改 `GameState`。

原则：

```text
GameState
    ↓
Agent Context
    ↓
Agent
    ↓
Decision / Action
    ↓
Rule Validation
    ↓
GameState
```

即：

> **Agent 负责提出行动，游戏规则负责验证和执行。**

这样即使未来加入大模型，核心游戏仍然属于确定性的游戏系统，而不是“让模型直接控制世界”。

## 十五、未来在线能力

初版不实现服务器。

未来增加以下能力时再引入后端：

```text
统计
注册
云存档
跨设备
排行榜
Agent API
```

在线统计应尽量采用事件化设计。

游戏内部可以产生：

```text
GameStarted
TurnCompleted
BattleFinished
GameCompleted
GameAbandoned
```

初版可以只在本地生成，不上传。

后续接入统计服务时再增加发送能力。

## 十六、技术边界

为了控制体量，初版明确避免：

* Java 后端
* 数据库
* 用户认证
* 服务端游戏逻辑
* 实时联机
* RTS 式单位控制
* 复杂 3D
* 大型前端状态管理框架
* 为未来需求提前实现整套服务器

技术设计的目标不是把所有未来能力提前做好，而是：

> **让第一版足够简单，同时不给未来演进留下结构性障碍。**
