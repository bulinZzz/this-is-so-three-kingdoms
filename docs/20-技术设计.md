# 这很三国｜技术设计

## 一、技术目标

游戏首先作为一个纯前端 Web 游戏运行。

初版不依赖后端、不要求账号、不需要购买服务器或域名。

目标是：

```text
浏览器
 ↓
加载静态资源
 ↓
在本地运行完整游戏
 ↓
本地保存游戏状态
```

部署采用 GitHub Pages。

## 二、技术栈

初版采用：

```text
TypeScript
Phaser 4
Vite
GitHub Pages
```

其中：

* TypeScript：游戏规则、状态与业务逻辑
* Phaser：2D 渲染、输入、场景、动画及游戏运行时
* Vite：开发、构建与静态资源打包
* GitHub Pages：静态网站部署

不引入 Java 后端。

不引入 React 作为游戏主框架。

## 三、整体架构

游戏逻辑与表现层分离。

```text
                Phaser
                  │
           游戏表现与输入
                  │
                  ↓
             Game Core
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
      Model     Rules    Simulation
        │         │         │
        └─────────┼─────────┘
                  ↓
              GameState
                  │
                  ↓
              SaveStore
```

核心原则：

> **游戏规则不依赖 Phaser。**

地图怎么画、按钮怎么显示、动画怎么播放，不应决定“这一季发生了什么”。

游戏规则应该可以在没有真实游戏画面的情况下独立运行。

## 四、核心状态模型

整个游戏围绕一个统一的 `GameState` 运行。

概念上包括：

```text
GameState
├── currentDate
├── currentTurn
├── actionPoints
├── actedCharacterIds
├── playerFaction
├── geography
├── factions
├── characters
├── history
└── randomState
```

`geography` 描述州与战略点的地理结构。战略点是领土与进攻的基本单位，记录其类型、所属州、相邻关系与当前归属势力（可能为空）。战略点在地图上的坐标与形状属于表现层，不进入状态。州是地理分组，用于地图展示与寻访范围；州归属按占点多寡判定，与他方并列时原归属者保持，因而须存状态，不能只由当前版图推出。

### 地图数据基准

州轮廓取自彩色分区底图，边界形状与底图一致，以建安十三年（208 年）的州制为准：

* 司隶领河东、河内、河南尹、弘农与三辅，建安年间司隶校尉督关中，长安属司隶。
* 凉州领陇右诸郡与河西四郡，武都、阴平自益州还入；汉中的底图分区与陇右同色，一并归凉州。
* 河西与陇右在底图上同用一片绿色，同属凉州；西海在底图上留白，不划入；居延的底图分区与河西同色，归凉州。
* 并州北缘含朔方、五原、云中，上郡故地（延安—榆林带）随底图分区并入并州。
* 底图未着色的地带（如阿拉善、鄂尔多斯、青海一带）不属任何州，保持无主；交州的下边界照底图的交州分区重描，西界沿底图分区的无主地一侧，海疆亦依底图轮廓；交州以南底图覆盖范围内的塞外陆地以底图为准，珠江口西岸的南沙、中山、珠海一带在底图上不着色，作无主陆地。
* 海岸线取历史岸线：渤海湾的现代黄河三角洲、苏北海岸与长江口北、珠江三角洲在近千年才淤积成陆，建安年间尚为海面或滩涂，不划入任何州，保持无主。
* 近岸岛屿的处理与参照底图一致：崇明、舟山群岛等保持无主，不并入最近的州。
* 塞外陆地不越出制图范围：南界止于北纬 16.3°，其以南的陆地与岛屿一概不取。

`factions` 记录势力：标识、名称、颜色与粮食 `grain`；粮食是初版唯一的资源，来源有两处：结束回合时按自有战略点的类型产量收取粮产（城市 300、关隘 150、野地 100，见 `src/core/economy.ts`），以及主动派部属征粮（`harvestGrain`，产量随该武将内政与自有战略点数）。

`characters` 记录武将：标识、姓名、状态、所属势力与所在州，以及武力 `might`、统率 `command`、智谋 `intellect`、内政 `politics`、势力倾向 `factionAffinity`、忠诚 `loyalty`、君主标记 `isMonarch`、驻地 `stationedSiteId`、兵力 `troops`、士气 `morale` 与寻访卡池层级 `tier`。在野者只记所在州，在仕者驻守各自势力的战略点；野心、声望、性格与年龄留待后续。

未出仕的武将是 `characters` 的一部分，不另外维护人才池。

`relations` 承载势力之间的外交关系，独立于各方实体模型，随迭代 9 引入；武将之间的关系属于另一个独立系统，初版不实现。

`history` 保存行动历史（类型、势力、时间、目标、结果），供表现层展示，不参与规则计算；回合推进不清空，全局累积。

开局由剧本（`Scenario`）给出：初始日期、玩家势力、势力与其粮食、地理与人物。`SCENARIOS` 汇集可选剧本，界面「新游戏」按所选剧本重建 `GameState` 并覆盖自动存档。剧本是纯数据，规则层与界面都不为某个剧本写分支。

具体模型根据实现逐步细化。

原则是：

> **世界状态只有一个事实来源。**

界面不自行维护第二份武将、战略点或资源数据。

## 五、规则系统

规则系统负责根据当前状态计算结果。

例如：

```text
advanceTurn()
resolveFactionActions()
resolveResourceProduction()
resolveConstruction()
resolveTalentSearch()
resolveConscription()
resolvePersonnel()
resolveDiplomacy()
resolveBattles()
resolveProvinceOwners()  // 占领后重算州归属
resolveFactionStatus()
resolveEvents()
updateOfficerStates()
```

这些操作应尽量保持确定性、可测试，并通过明确的输入与输出修改 `GameState`。

当前已实现的规则：回合推进（`advanceTurn`，含按领地收取粮产 `collectGrain` 与按统率自然增兵 `growTroops`）、寻访人才（`seekTalent`）、征兵（`recruit`）、征粮（`harvestGrain`）、调动（`transfer`，可一次调多名）、进攻与战斗（`attack`，主将、副将与军师的编成）；其余为后续迭代的规划。

### 随机性

游戏包含人才寻访、事件、战斗等随机结果。

随机数集中管理，并支持可复现的随机种子；分两条互不干扰的流：模拟流内部状态随存档落盘，用于战斗、AI 与事件等世界演化，同一存档可复现同一结果；抽卡流会话级、不落盘，用于玩家主动发起的抽取，读档与刷新都不回退。

集中管理便于重现问题、调试异常战斗与验证规则，也为未来的固定种子或挑战模式留出基础。

## 六、行动力系统

行动力属于游戏规则层。每项行动声明自己的行动力成本，成本集中在常量表中定义，不散落在规则里；具体数值见《游戏机制》。

行动执行流程：

```text
玩家请求行动
 ↓
检查前置条件
 ↓
检查行动力
 ↓
扣除行动力
 ↓
执行规则
 ↓
更新 GameState
 ↓
写入行动记录
 ↓
刷新界面
```

## 七、武将与势力系统

势力由君主统领，君主是该势力中的一名武将，每个势力有且只有一名君主；势力自身记录标识、名称、颜色与粮食。

武将的字段见「核心状态模型」中的 `characters`。四项能力分工明确：统率决定兵力（自然增长的快慢与征兵产量），智谋用于战斗，武力用于单挑，内政决定征粮产量。

兵力直接记在武将身上（`troops`），势力不存在脱离武将的兵力；部队与兵种的模型暂不细化，兵种留待后续。

兵力增长分两条路：每季结束由 `growTroops` 让各势力在仕武将按统率自然补充，增量只与统率有关、带固定幅度的浮动，各方一视同仁；征兵（`recruit`）是主动的补充手段，产量按统兵者的统率换算、粮食按同一基准消耗（一兵一粮），并占用该武将本季的行动。粮食同样两条路：每季的领地粮产与主动的征粮（`harvestGrain`），后者产量随该武将内政与势力自有战略点数。每名武将有带兵上限（统率 × 150），自然增长与征兵都补到上限即止。

士气由 `morale` 记录，当前恒为满值，参与战力计算；改变士气的途径（单挑）尚无入口。

`status` 描述武将的处境：在野、在仕、被俘、退场。战略点失守时，守军每名武将按权重判定逃亡、战死或被俘；被俘的处置（招降、释放、处决）尚未实现，暂按退场处理，无城可投者流落为在野。退场的武将不再参与游戏。

`factionAffinity` 与 `loyalty` 目前是静态字段，不参与计算。忠诚由基础倾向、所属势力、待遇、历史经历与近期事件共同决定的设计，留待迭代 7 实现。

## 八、战斗系统

战斗系统接收双方部队及环境状态，生成战斗结果。

输入包括：

```text
主将
兵力
兵种
士气
地形
战前策略
特殊能力
```

输出包括：

```text
胜负
伤亡
剩余兵力
士气变化
主将状态
占领结果
战斗日志
```

战斗结算与展示分离：规则层只产出胜负、伤亡与占领结果并写入历史，表现层读取这份结果，将来加入战斗动画也不必重写规则。

初版不实现单位实时寻路与即时操作。

初版在规则层直接结算，不单独实现战斗场景：`attack` 接收一份编成（`AttackParty`，主将必选，副将、军师可选）与目标战略点，`partySide` 把编成折算为战力要素——兵力为三人之和、智谋取三人中最高者、士气取主将，与守方相乘比较，守方再乘防守补正，双方各带 ±10% 的随机浮动。编成者须驻守在与目标相邻的自有战略点且本季未行动；`isAttackable` 判断战略点是否与自有领地接壤（据此显示进攻入口），`attackCandidates` 列出候选之人（含本季已行动者，由界面标出不可选）。守军同样至多三人迎战：`garrisonAt` 从该战略点的守军中取兵力最多的三名，其中统率最高者为主将、智谋最高者为军师，本季已经行动过的守军只计半数兵力；这样败军退守堆在一处也不会让最后一城无止境地变强。无主战略点没有守军。只接战的双方受损：胜方参战部队一同前移进驻，败方各自退回原驻地并受损。战略点失守时由 `resolveDefenders` 结算每名守军（含未接战者）的去向：约一半撤往自有的战略点，其余战死或被俘，任何战略点（含覆灭之战）都按同一套权重判定，君主只在本势力尚未覆灭时必定撤退；本势力再无城池可投时，逃亡者流落为在野（卡池层级暂给基础池，按能力与身份细分留待迭代 7）。势力是否覆灭由 `isFactionDestroyed` 判定——失去全部战略点，或麾下不再有任何在仕武将；界面据此在势力栏标出「已覆灭」。战斗只改变归属与兵力，不改变地理结构。

结算还给出一份战报（`BattleReport`）：攻守双方的主将、参战武将、投入兵力、战力（含防守补正与随机浮动）、伤亡与剩余。战报随行动记录写入历史，界面读取后在战后弹出，作为战斗过程的呈现；伤亡与剩余只反映战损，不含失守后撤退、战死或被俘的武将。将来加入战斗动画时复用同一份战报。

调动与进攻同为「以目标战略点为起点」的行动：`isTransferTarget` 判断该战略点是否自有且与别的自有战略点相邻，`transferCandidates` 列出可调入的部属，`transfer` 接收一组标识，按人数累加行动力（`ActionRequest.cost`）。

单挑目前只做士气结算：对方拒战则其士气下降，应战则胜者升、败者降；致阵亡留待后续，且尚无界面入口。

## 九、世界模拟

其他势力不能直接调用 UI。

其他势力的主要行动对玩家可见。

它们通过统一的势力决策接口执行行动：

```text
FactionDecision
    ↓
Action
    ↓
Rule Validation
    ↓
Execute
```

初版 AI 采用规则驱动，而不是 Agent。

决策主要依据：

* 当前资源
* 领土
* 敌我关系
* 军力
* 人才
* 安全程度
* 势力目标
* 当前局势

目标是让各势力具有可理解的行为倾向，而不是追求真正意义上的智能。

## 十、事件系统

事件采用数据驱动方式。

概念结构：

```text
GameEvent
├── id
├── type
├── trigger
├── weight
├── conditions
├── effects
└── message
```

### 事件约束

初版事件的 `effects` **只能操作已有的游戏属性与状态**，不允许通过事件新增游戏的基础机制。

事件可以自动结算，也可以要求玩家在若干选项中做出选择；两种形式的结果都只是已有属性与状态的变化。

初版不预先维护一份可改属性的清单，具体改哪些属性由事件本身决定，只要落在已有属性与状态上即可。

不允许事件直接引入：

```text
new_relation_type
new_combat_rule
new_action_type
new_resource_type
```

除非该机制已经正式成为核心游戏规则的一部分。

这样可以保证新增事件主要是内容扩展，而不是底层系统扩展。

### 事件执行

事件处理流程：

```text
检查触发条件
 ↓
选定事件
 ↓
计算 Effects
 ↓
修改 GameState
 ↓
生成 EventResult
 ↓
表现层展示事件
```

事件效果与事件表现分离。

例如：

```text
EventRule
    ↓
EventResult
    ↓
EventPanel
```

界面不参与事件规则判断。

### 后续扩展

如果后续某类事件被验证为具有足够的游戏价值，可以将其从普通属性事件扩展为持续效果或专属机制。

这种扩展应作为核心规则演进处理，而不通过普通事件系统绕过现有边界。

## 十一、存档

初版采用本地自动存档。

存储：

```text
SaveData
├── schemaVersion
└── gameState
```

`randomState` 属于 `gameState` 的一部分，随其一起落盘。

进入下一回合时自动保存；行动本身不落盘，读档或刷新会退回到本回合开始时的进度。

保存层定义抽象接口：

```text
SaveStore
├── save()
└── load()
```

初版实现：

```text
LocalSaveStore
```

实际存储优先使用 `localStorage`；只有当后续状态规模明显超出适合范围时，再考虑迁移至 IndexedDB。

保存数据必须带版本号，以支持未来数据结构升级。

## 十二、前端入口

项目由 Vite 构建为静态网站。

典型流程：

```text
GitHub Repository
        ↓
GitHub Actions
        ↓
vite build
        ↓
dist/
        ↓
GitHub Pages
```

游戏入口为普通网页。

用户访问地址后直接加载游戏，不需要安装客户端。

初版主要面向桌面浏览器。

移动浏览器适配属于后续工作。

## 十三、资源与美术

所有游戏资源作为静态前端资源随版本发布。

建议统一：

```text
assets/
├── portraits/
├── map/
├── icons/
├── ui/
├── effects/
└── audio/
```

图片、图标和音频不参与游戏规则。

武将头像、地图、UI 等美术资源只承担表现职责。

第一阶段允许使用临时素材占位，以保证玩法优先。

正式资源应尽量统一画面比例、构图与视觉语言，形成项目自己的美术体系。

## 十四、未来 Agent 能力

Agent 不属于初版核心架构。

未来如果加入 Agent，应作为可替换的决策实现，而不是让 LLM 直接修改 `GameState`。

原则：

```text
GameState
    ↓
Agent Context
    ↓
Agent
    ↓
Decision / Action
    ↓
Rule Validation
    ↓
GameState
```

即：

> **Agent 负责提出行动，游戏规则负责验证和执行。**

这样即使未来加入大模型，核心游戏仍然属于确定性的游戏系统，而不是“让模型直接控制世界”。

## 十五、未来在线能力

初版不实现服务器。

未来增加以下能力时再引入后端：

```text
统计
注册
云存档
跨设备
排行榜
Agent API
```

在线统计应尽量采用事件化设计。

游戏内部可以产生：

```text
GameStarted
TurnCompleted
BattleFinished
GameCompleted
GameAbandoned
```

初版可以只在本地生成，不上传。

后续接入统计服务时再增加发送能力。

## 十六、技术边界

为了控制体量，初版明确避免：

* Java 后端
* 数据库
* 用户认证
* 服务端游戏逻辑
* 实时联机
* RTS 式单位控制
* 复杂 3D
* 大型前端状态管理框架
* 为未来需求提前实现整套服务器

技术设计的目标不是把所有未来能力提前做好，而是：

> **让第一版足够简单，同时不给未来演进留下结构性障碍。**
