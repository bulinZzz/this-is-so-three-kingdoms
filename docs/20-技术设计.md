# 这很三国｜技术设计

## 一、技术目标

游戏首先作为一个纯前端 Web 游戏运行。

初版不依赖后端、不要求账号、不需要购买服务器或域名。

目标是：

```text
浏览器
 ↓
加载静态资源
 ↓
在本地运行完整游戏
 ↓
本地保存游戏状态
```

部署采用 GitHub Pages。

## 二、技术栈

初版采用：

```text
TypeScript
Phaser 4
Vite
GitHub Pages
```

其中：

* TypeScript：游戏规则、状态与业务逻辑
* Phaser：2D 渲染、输入、场景、动画及游戏运行时
* Vite：开发、构建与静态资源打包
* GitHub Pages：静态网站部署

不引入 Java 后端。

不引入 React 作为游戏主框架。

## 三、整体架构

游戏逻辑与表现层分离。

```text
                Phaser
                  │
           游戏表现与输入
                  │
                  ↓
             Game Core
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
      Model     Rules    Simulation
        │         │         │
        └─────────┼─────────┘
                  ↓
              GameState
                  │
                  ↓
              SaveStore
```

核心原则：

> **游戏规则不依赖 Phaser。**

地图怎么画、按钮怎么显示、动画怎么播放，不应决定“这一季发生了什么”。

游戏规则应该可以在没有真实游戏画面的情况下独立运行。

## 四、核心状态模型

整个游戏围绕一个统一的 `GameState` 运行。

概念上包括：

```text
GameState
├── currentDate
├── currentTurn
├── playerFaction
├── geography
├── factions
├── officers
├── armies
├── relations
├── events
├── history
├── randomState
└── gameMeta
```

`geography` 描述州与战略点的地理结构。战略点是领土与进攻的基本单位，记录其类型、所属州、相邻关系与当前归属势力（可能为空）。战略点在地图上的坐标与形状属于表现层，不进入状态。州在初版作为地理分组，用于地图展示与人才寻访范围；州归属在迭代 4 引入，按占点多寡判定，归属势力字段随实现加入。

### 地图数据基准

州轮廓取自彩色分区底图，边界形状与底图一致，以建安十三年（208 年）的州制为准：

* 司隶领河东、河内、河南尹、弘农与三辅，建安年间司隶校尉督关中，长安属司隶。
* 凉州领陇右诸郡与河西四郡，武都、阴平自益州还入；汉中的底图分区与陇右同色，一并归凉州。
* 河西与陇右在底图上同用一片绿色，同属凉州；西海在底图上留白，不划入；居延的底图分区与河西同色，归凉州。
* 并州北缘含朔方、五原、云中，上郡故地（延安—榆林带）随底图分区并入并州。
* 底图未着色的地带（如阿拉善、鄂尔多斯、青海一带）不属任何州，保持无主；交州的下边界照底图的交州分区重描，西界沿底图分区的无主地一侧，海疆亦依底图轮廓；交州以南底图覆盖范围内的塞外陆地以底图为准，珠江口西岸的南沙、中山、珠海一带在底图上不着色，作无主陆地。
* 海岸线取历史岸线：渤海湾的现代黄河三角洲、苏北海岸与长江口北、珠江三角洲在近千年才淤积成陆，建安年间尚为海面或滩涂，不划入任何州，保持无主。
* 近岸岛屿的处理与参照底图一致：崇明、舟山群岛等保持无主，不并入最近的州。
* 塞外陆地不越出制图范围：南界止于北纬 16.3°，其以南的陆地与岛屿一概不取。

未效忠与在野的武将是 `officers` 的一部分，不另外维护人才池。

`relations` 承载势力之间的外交关系，独立于各方实体模型；武将之间的关系属于另一个独立系统，初版不实现。

`history` 保存行动历史（类型、势力、时间、目标、结果），供表现层展示，不参与规则计算；回合推进不清空，全局累积。

具体模型根据实现逐步细化。

原则是：

> **世界状态只有一个事实来源。**

界面不自行维护第二份武将、战略点或资源数据。

## 五、规则系统

规则系统负责根据当前状态计算结果。

例如：

```text
advanceTurn()
resolveFactionActions()
resolveResourceProduction()
resolveConstruction()
resolveTalentSearch()
resolveConscription()
resolvePersonnel()
resolveDiplomacy()
resolveBattles()
resolveOccupancyControl()  // 战略点占有变化与州归属重算（迭代 4）
resolveFactionStatus()
resolveEvents()
updateOfficerStates()
```

这些操作应尽量保持确定性、可测试，并通过明确的输入与输出修改 `GameState`。

### 随机性

游戏包含人才寻访、事件、战斗等随机结果。

随机数集中管理，并支持可复现的随机种子；分两条互不干扰的流：模拟流内部状态随存档落盘，用于战斗、AI 与事件等世界演化，同一存档可复现同一结果；抽卡流会话级、不落盘，用于玩家主动发起的抽取，读档与刷新都不回退。

集中管理便于重现问题、调试异常战斗与验证规则，也为未来的固定种子或挑战模式留出基础。

## 六、行动力系统

行动力属于游戏规则层。每项行动声明自己的行动力成本，成本集中在常量表中定义，不散落在规则里；具体数值见《游戏机制》。

行动执行流程：

```text
玩家请求行动
 ↓
检查前置条件
 ↓
检查行动力
 ↓
扣除行动力
 ↓
执行规则
 ↓
更新 GameState
 ↓
写入行动记录
 ↓
刷新界面
```

## 七、武将与势力系统

武将模型至少包括：

```text
Officer
├── id
├── stats
├── age
├── currentFaction
├── loyalty
├── fame
├── ambition
├── factionAffinity
├── personality
├── troops
├── morale
└── status
```

势力由君主统领，君主是该势力中的一名武将，具有特殊地位。

兵力以部队（`armies`）为载体，由武将统率，征兵直接编入部队；`troops` 是武将所统率部队的兵力。部队与兵种的模型暂不细化。

士气暂时作为武将属性，由 `morale` 记录。

`status` 描述武将的处境（在野、在仕、被俘、退场等）。因战死或被俘处置而退场的武将不再参与游戏。

`factionAffinity` 属于内部模型，不直接暴露原始数值。

最终忠诚度由多个因素共同决定：

```text
基础倾向
+
当前所属势力
+
待遇
+
历史经历
+
近期事件
```

计算结果影响：

* 加入
* 留任
* 招降
* 离开
* 特殊行为

这样人物不会被单一字段决定。

## 八、战斗系统

战斗系统接收双方部队及环境状态，生成战斗结果。

输入包括：

```text
主将
兵力
兵种
士气
地形
战前策略
特殊能力
```

输出包括：

```text
胜负
伤亡
剩余兵力
士气变化
主将状态
占领结果
战斗日志
```

战斗模拟和战斗展示分离。

例如：

```text
BattleEngine
    ↓
BattleResult
    ↓
BattleScene
```

因此以后即使修改战斗动画，也不需要重写战斗规则。

初版不实现单位实时寻路与即时操作。

## 九、世界模拟

其他势力不能直接调用 UI。

其他势力的主要行动对玩家可见。

它们通过统一的势力决策接口执行行动：

```text
FactionDecision
    ↓
Action
    ↓
Rule Validation
    ↓
Execute
```

初版 AI 采用规则驱动，而不是 Agent。

决策主要依据：

* 当前资源
* 领土
* 敌我关系
* 军力
* 人才
* 安全程度
* 势力目标
* 当前局势

目标是让各势力具有可理解的行为倾向，而不是追求真正意义上的智能。

## 十、事件系统

事件采用数据驱动方式。

概念结构：

```text
GameEvent
├── id
├── type
├── trigger
├── weight
├── conditions
├── effects
└── message
```

### 事件约束

初版事件的 `effects` **只能操作已有的游戏属性与状态**，不允许通过事件新增游戏的基础机制。

事件可以自动结算，也可以要求玩家在若干选项中做出选择；两种形式的结果都只是已有属性与状态的变化。

初版不预先维护一份可改属性的清单，具体改哪些属性由事件本身决定，只要落在已有属性与状态上即可。

不允许事件直接引入：

```text
new_relation_type
new_combat_rule
new_action_type
new_resource_type
```

除非该机制已经正式成为核心游戏规则的一部分。

这样可以保证新增事件主要是内容扩展，而不是底层系统扩展。

### 事件执行

事件处理流程：

```text
检查触发条件
 ↓
选定事件
 ↓
计算 Effects
 ↓
修改 GameState
 ↓
生成 EventResult
 ↓
表现层展示事件
```

事件效果与事件表现分离。

例如：

```text
EventRule
    ↓
EventResult
    ↓
EventPanel
```

界面不参与事件规则判断。

### 后续扩展

如果后续某类事件被验证为具有足够的游戏价值，可以将其从普通属性事件扩展为持续效果或专属机制。

这种扩展应作为核心规则演进处理，而不通过普通事件系统绕过现有边界。

## 十一、存档

初版采用本地自动存档。

存储：

```text
SaveData
├── schemaVersion
├── gameVersion
├── gameState
└── meta
```

`randomState` 属于 `gameState` 的一部分，随其一起落盘。

默认在完成回合后自动保存。

保存层定义抽象接口：

```text
SaveStore
├── save()
└── load()
```

初版实现：

```text
LocalSaveStore
```

实际存储优先使用 `localStorage`；只有当后续状态规模明显超出适合范围时，再考虑迁移至 IndexedDB。

保存数据必须带版本号，以支持未来数据结构升级。

## 十二、前端入口

项目由 Vite 构建为静态网站。

典型流程：

```text
GitHub Repository
        ↓
GitHub Actions
        ↓
vite build
        ↓
dist/
        ↓
GitHub Pages
```

游戏入口为普通网页。

用户访问地址后直接加载游戏，不需要安装客户端。

初版主要面向桌面浏览器。

移动浏览器适配属于后续工作。

## 十三、资源与美术

所有游戏资源作为静态前端资源随版本发布。

建议统一：

```text
assets/
├── portraits/
├── map/
├── icons/
├── ui/
├── effects/
└── audio/
```

图片、图标和音频不参与游戏规则。

武将头像、地图、UI 等美术资源只承担表现职责。

第一阶段允许使用临时素材占位，以保证玩法优先。

正式资源应尽量统一画面比例、构图与视觉语言，形成项目自己的美术体系。

## 十四、未来 Agent 能力

Agent 不属于初版核心架构。

未来如果加入 Agent，应作为可替换的决策实现，而不是让 LLM 直接修改 `GameState`。

原则：

```text
GameState
    ↓
Agent Context
    ↓
Agent
    ↓
Decision / Action
    ↓
Rule Validation
    ↓
GameState
```

即：

> **Agent 负责提出行动，游戏规则负责验证和执行。**

这样即使未来加入大模型，核心游戏仍然属于确定性的游戏系统，而不是“让模型直接控制世界”。

## 十五、未来在线能力

初版不实现服务器。

未来增加以下能力时再引入后端：

```text
统计
注册
云存档
跨设备
排行榜
Agent API
```

在线统计应尽量采用事件化设计。

游戏内部可以产生：

```text
GameStarted
TurnCompleted
BattleFinished
GameCompleted
GameAbandoned
```

初版可以只在本地生成，不上传。

后续接入统计服务时再增加发送能力。

## 十六、技术边界

为了控制体量，初版明确避免：

* Java 后端
* 数据库
* 用户认证
* 服务端游戏逻辑
* 实时联机
* RTS 式单位控制
* 复杂 3D
* 大型前端状态管理框架
* 为未来需求提前实现整套服务器

技术设计的目标不是把所有未来能力提前做好，而是：

> **让第一版足够简单，同时不给未来演进留下结构性障碍。**
