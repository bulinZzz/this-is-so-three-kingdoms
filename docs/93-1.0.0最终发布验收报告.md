## 二、CI 执行结果

工作流顺序：

```text
npm ci
  ↓
npm test
  ↓
npm run acceptance
  ↓
npm run build（含 tsc --noEmit）
  ↓
上传 Pages 产物
  ↓
部署
```

`deploy` 任务使用 `needs: build`。验收命令以非零退出时，`build` 任务失败，部署任务不会执行。`tests/releaseWorkflow.test.ts` 对「单元测试 → 验收 → 构建 → 上传」的顺序与 `needs: build` 做静态回归检查。

本地执行结果：

- `npm ci`：通过，39 个包。
- `npm test`：37 文件、500 项通过。
- `npm run acceptance`：4 项通过，耗时约 10 秒。
- `npm run build`：通过；产物约 1.8 MB，gzip 约 489 KB。
- `npx tsc --noEmit`：通过（构建阶段已包含）。

远端执行结果：提交 `8ca1264` 推送后，「部署到 GitHub Pages」工作流在 GitHub-hosted Runner 上跑通，单元测试、验收推演、生产构建与 Pages 部署全部成功。

## 三、正式剧本验证

### 固定种子推演

`npm run acceptance`，正式剧本，种子 208，上限 160 季：

- 30 战 23 夺。
- 荆南第 29 季、士燮第 77 季、刘璋第 157 季、南蛮第 159 季覆灭。
- 刘备未覆灭，但跑满 160 季仍未统一。
- 临时事件「南郡风云」已把夷陵、秭归交给刘备，西川方向已打开；后期主要在曹操、孙权方向受阻。

### 放宽季数上限的追加验证

为判断「推演无法统一」是季数不足还是交换比问题，把季数上限临时放宽到 400 季与 800 季各跑一次；跑完已还原为 160 季，验收口径不变。

| 上限 | 结局 | 战绩 | 覆灭势力 |
| --- | --- | --- | --- |
| 160 季 | 未统一 | 30 战 23 夺 | 荆南 29、士燮 77、刘璋 157、南蛮 159 |
| 400 季 | 未统一 | 57 战 31 夺 | 再加张鲁 190 |
| 800 季 | 未统一 | 110 战 37 夺 | 再加马腾 720；第 744 季向孙权宣战，夺取赤壁、柴桑、东冶、建业 |

- 单城耗时随目标变强迅速拉长：陈仓第 194 季两波皆败、第 226 季才下（32 季）；槐里第 227、241、256 季各败两波，第 304 季才下（77 季）；西平关第 545 季起连续受阻 19 次，第 720 季才下（175 季）。
- 第 400 季到第 800 季的这两百年只多取六处。
- 800 季终局仍余曹操 20 处、孙权 4 处、公孙康 4 处；曹操的中原、河北与江陵襄阳一线一次未攻。

结论：代理没有卡死，推进方向正确，但单季投送能力（一季两波、每波至多五人）对上守方六队加据点补正，决定了每座坚城的成本是几十到上百季；按后期节奏清完剩余版图仍需上千季。这是交换比问题，不是季数问题。

### 额外修复：前排被击溃后的接战

原实现中，后排近战在任何情况下都没有可攻击目标，只能等待出击或待机。实际表现是刘关张前排全部溃败后，后排赵云仍只有出击选项、无法直接攻击。现改为：本方前排已无存活队伍时，后排即成为第一排，近战可直接攻击；骑兵的指令不再包含出击。新增「前排三队全灭后后排骑兵直接攻击」用例，并保留「前排未空时骑兵须先出击」的旧用例。

### 多随机种子压力测试

20 个种子 × 60 季：

- 19/20 未结束，1 个种子（16）第 42 季覆灭。
- 13 个种子打灭 1 家，7 个种子打灭 0 家。
- 9/20 出现长期无版图变化（20 季以上）。
- 逐季不变量检查 0 异常。
- 同种子重跑状态完全一致。

长局 5 个种子 × 200 季：

- 5/5 未结束。
- 2 个种子打灭 4 家，3 个种子各打灭 1 家。
- 3/5 长期无版图变化。
- 逐季不变量检查 0 异常。

### 原因分析

1. **代理策略不足**：代理不做求和，不会在僵持后换目标；不围绕「控制整州解锁高阶层在野武将」做定向扩张；两波进攻的编成偏保守，第一波常只派够用的少数人，第二波难以形成十人规模的持续压力。
2. **随机性敏感**：固定种子 208 的抽卡流能招到较好的武将，成绩明显好于压力测试中变化的抽卡种子；这解释了同规则下不同种子的差异，但不改变后期僵局的结构性原因。
3. **规则层面的攻城僵局**：攻方一季 10 点行动力至多支撑两次进攻，每次至多 5 人，共 10 人；守方每城可出 6 队（5 名自选加驻将），大势力名册厚，一季内可以轮换出两组守将，合计 12 人。双方兵力都撞上带兵上限后，守方还有据点补正，攻方的质量优势不足以稳定抵消人数与补正，形成反复失败但双方都难以推进的僵局。
4. **AI 势力之间的僵局**：AI 不主动向中立势力宣战，战火由玩家点燃；玩家一旦与大国开战且打不动，也没有自动缓和机制，容易长期停在单一战场。

### 未采取的修改

本轮没有修改攻方或守方的编成上限，也没有削弱守军。曾临时把守方自选人数从 5 降到 4 做对照，正式剧本在 200 季内仍未统一，随后已还原，未留下规则改动。该问题与《想法记录》中「坚城的破局手段」一致，适合后续用兵种、武将技能或围城机制解决。

### 人工验收步骤

1. 在无开发者模式的正式构建中新建「建安十三年」，按正常规则游玩。
2. 前 20 季内完成寻访、征兵与荆南攻略；记录是否能在 10 点行动力内组织两次有效进攻。
3. 打灭荆南后，尝试取得赤壁或荆北一处，使荆州归属转到刘备，观察高阶层在野武将是否解锁并可招募。
4. 中期打灭交州或孙权，记录兵力、粮草、武将与关键战斗。
5. 后期集中进攻夷陵、襄阳或江陵，连续两波进攻并记录守军人数、守将轮换、双方战损；若仍无法攻下，记录具体回合与数值。
6. 在任何阶段保存到手动槽位，刷新页面后读回，确认回合与局面一致。
7. 输出完整通关记录；若未通关，按「策略问题 / 随机问题 / 规则问题」分类说明。

## 四、存档与浏览器验证

### 存档深层校验

新增校验覆盖：

- 顶层结构合法但数组元素不合法（如相邻列表含非字符串）。
- 武将缺少活动范围。
- 势力粮食为 NaN。
- 在仕武将引用不存在的势力。
- 战略点引用不存在的势力。
- 战略点类型、武将状态、兵种、关系类型等枚举非法。
- 势力关系、接触名单、俘虏记录指向不存在的对象。
- 行动历史日期不合法。
- 武将能力超过强化上限（120）。
- 已结束的对局缺少结束回合。
- 行动力为负数。

以上全部返回 `invalid`，不进入对局。20 季连续推进后的存档每季保存并读回，均通过深层校验并保持一致。

同时修正了一处校验与规则不一致：武将强化后的能力上限为 120，原人物校验只允许 100；现已允许 120、拒绝 121。势力覆灭时原君主转为在野、被斩杀后退场时，`isMonarch` 一并清除；被俘君主保留君主身份，仍不可劝降或释放。

### 多标签页

产品行为明确为「同一存档不支持多标签页并行游玩」。其他标签页写入自动存档或手动槽位后，本页通过 `storage` 事件检出冲突，停止自动保存与手动保存，并提示刷新或重新读档；重新读档或新开一局后解除。单元测试覆盖：冲突后自动存档不覆盖、手动槽位不写入、读档后解除、新开局后解除。

未执行真实双标签页浏览器手工操作；冲突逻辑由单元测试覆盖，界面提示由浏览器链路间接确认。

### 浏览器链路

已通过真实浏览器验证三条链路：

1. 开始正式剧本 → 公安寻访（寻到简雍）→ 打开武将名册 → 结束回合并等待他方行动 → 保存到槽位 1 → 刷新 → 从槽位 1 读档，回到第 2 回合。
2. 读取槽位 1 → 外交向荆南宣战 → 进攻武陵 → 选关羽、张飞、赵云编成 → 开战 → 张飞攻击金旋并产生战况 → 自动战斗 → 战报「战斗告捷」并攻占武陵 → 收兵后棋盘仍可操作。
3. 以荆南四郡尽归刘备、荆南已覆灭的存档读档后结束回合 → 弹出「南郡风云」叙事 → 确定关闭 → 夷陵、秭归归刘备，刘曹与刘孙为中立，事件写入历史。

未验证项：真实人工从开局打到统一或覆灭的完整长局。

## 五、剩余风险

### 已接受：推演无法统一（不阻塞 1.0.0）

- 160、400、800 季三次推演均未统一，且单城成本随对手变强而急剧上升；判断为交换比问题，不是季数问题。
- 项目决定：不必在 1.0.0 解决，先发布；破局手段（兵种、武将技能、围城断粮等）留待后续版本。
- 没有真实人工完整通关记录；若人工同样受阻，按《想法记录》的设想处理。

### 已确认：远端工作流与 Pages 部署

- 提交 `8ca1264` 推送后，GitHub-hosted Runner 上「部署到 GitHub Pages」工作流通过，单元测试、验收推演、生产构建与 Pages 部署全部成功。

### 可以接受的已知限制

- 事件内容仅一条临时事件；武将头像为占位；他方只做最小行为集；地图无领土色与边界；移动端未适配。
- 同一存档不支持多标签页并行游玩，但已明确提示并停止写入。
- 构建体积警告。

### 适合 1.1 及以后

- 兵种相克、武将技能、百分比伤害、暗杀、围城断粮等破局手段。
- 他方 AI 的择优编成、兵力集中与抓住空档。
- 事件内容与对话演出。
- 真实人工长局平衡调优。

## 六、最终发布建议

**CONDITIONAL GO：先发 1.0.0。**

理由：自动化门禁、存档与 Actions 兼容性已经达标；正式剧本无法靠推演统一已确认是交换比问题，项目决定不作为 1.0.0 的阻塞项，改由后续版本的破局手段解决。发布时按此顺序收尾：

1. 推送本轮改动，在 GitHub Actions 上跑完整工作流，确认测试、验收、构建与 Pages 部署全部通过后宣布 1.0.0。
2. 发布说明写明：自动化推演无法统一，坚城的破局手段留待后续版本。
3. 后续版本按《想法记录》的手段验证破局（同一坚城连打两波、记录守军与可用守将的递减），再重新评估统一路径。
